# 전처리 변경과 평가 근거 재사용 프레임워크

상태: **연구용 제안 v0.1.0 — 거버넌스 효과를 실증 검증하지 않음**

## 1. 연구 질문과 판단 단위

이 프레임워크는 “전처리를 바꾸었을 때 어떤 기존 평가 근거가 여전히 유효하며, 무엇을 새로 확인해야 하는가?”를 다룹니다. 법적으로 새 적합성 평가가 필요한지는 별도의 검토 축입니다.

판단 단위는 전처리 함수의 이름이 아니라 **시스템·변경·평가 주장·사용 맥락·기존 근거의 묶음**입니다. 같은 정규화, 리사이즈, 결측값 처리도 대상 집단이나 방어 기능에 따라 영향이 달라집니다. 한 시험의 결과를 재사용할 수 있다는 사실은 다른 시험이나 전체 적합성 평가도 재사용할 수 있다는 뜻이 아닙니다.

이 구현은 사람이 제출한 입력된 필수 항목의 충족과 일관성을 확인하여 검토 경로를 제시합니다. 숨은 의존성 탐색, 공격 탐지, 실시간 운영 감시, 법적 판정은 구현 범위에 포함되지 않습니다.

## 2. 두 판단 축

### 기술적 근거의 재사용

다음 순서로 판단합니다. 위에 있는 조건이 아래의 재사용 조건보다 우선합니다.

1. **형식 확인:** 유효하지 않은 값이나 스키마는 `HOLD`로 처리하고 오류를 보여 줍니다.
2. **반증 확인:** 알려진 회귀 또는 하나 이상의 실패한 시험이 있으면 `INVALIDATED`입니다. 다른 항목의 통과나 동일한 지문이 실패를 덮지 않습니다.
3. **관련 변화 확인:** 완전한 지문 쌍 중 차이가 있거나, 보호조치·입력 집단·사용 목적이 바뀌거나, 평가 범위 유지·결정성·의존성 범위 조건이 부정되면 `RETEST_REQUIRED`입니다.
4. **근거 공백 확인:** 기존 통과를 확인하지 못했거나 주장·참조가 없거나 핵심 조건·지문이 미완성이면 `HOLD`입니다.
5. **제한된 재사용:** 아래 조건을 모두 충족하면 `REUSE_SCOPED`입니다.

`REUSE_SCOPED`의 입력 조건은 다음과 같습니다.

- 재사용할 평가 주장과 기존 평가의 참조가 있고 기존 결과가 통과로 기록되어 있습니다.
- 모델, 실제 검사 입력, 정답, 평가기, 정책, 실행 조건의 여섯 지문 쌍이 모두 완전하고 일치합니다.
- 결정성, 의존성 범위의 충족, 평가 범위 유지가 `yes`입니다.
- 보호조치 변화, 입력 집단 변화, 알려진 회귀, 사용 목적 변화가 모두 `no`입니다.

이 조건은 자동으로 발견한 사실이 아니라 제출된 사실과 선언입니다. 형식상 유효한 해시도 잘못된 파일을 대표할 수 있고, 같은 실행 환경 기록도 빠진 외부 상태를 숨길 수 있습니다. 해시 충돌이 없고, 모든 평가 관련 입력과 실행 의미가 동일하며, 계산이 결정적이라는 조건 아래 고정 평가 결과의 동일성을 논의할 수 있습니다.

`not_run`은 실패와 같지 않지만 통과 근거도 아닙니다. 이 도구는 어떤 새 시험을 의무적으로 실행해야 하는지 도메인별로 자동 결정하지 않습니다. 필요한 시험과 주장별 의존성의 범위를 검토자가 정의해야 합니다.

### 규제 검토

규제 결과는 법적 결론이 아니라 사람이 검토해야 할 경로입니다.

| 경로 | 주요 입력 상태 | 출력의 범위 |
| --- | --- | --- |
| `REVIEW_REQUIRED` | 사용 목적 또는 준수 영향이 있다고 선언됨. 또는 고위험·출시·이전 평가가 확인되었지만 변경 계획이 없거나 불명확하거나 참조가 없음 | 실질적 변경 및 필요한 평가 절차 검토 요청 |
| `CONTEXT_REQUIRED` | 적용 맥락, 이전 평가, 목적·준수 영향 등에 필요한 정보가 부족함 | 자료 확보 요청 |
| `OUT_OF_SCOPE` | 출시 전이거나, 목적·준수 영향 없음과 고위험 아님이 입력됨. 알려진 목적·준수 우려 등 우선 조건은 별도 검토 | 이 도구가 다루는 특정 Article 43(4) 경로 밖 |
| `DOCUMENTED_PATH` | 고위험·출시·이전 평가, 계획과 참조가 있고 목적·준수 영향 없음과 법적 맥락 참조가 기록됨 | 검토 경로의 문서화. 면제나 승인 판정이 아님 |

고위험으로 선언된 시스템에서 기술적 결과가 `INVALIDATED`이면 규제 축도 `REVIEW_REQUIRED`로 넘깁니다. 동시에 준수 영향이 없다고 입력되었다면 모순을 경고합니다. 고정 시험 실패가 법적 substantial modification을 자동으로 증명하는 것은 아니며, 상충하는 근거를 사람이 검토하도록 하는 보수적인 규칙입니다.

목적·준수 영향이 `unknown`이어도 출시 전이라는 명시적 입력이 있고 우선 우려 조건이 없으면, 이미 출시된 시스템의 변경이라는 특정 경로에 대해 `OUT_OF_SCOPE`가 될 수 있습니다. 고위험이 아니라고 입력했지만 출시 전임이 확인되지 않고 목적 또는 준수 영향이 미확인이면 `CONTEXT_REQUIRED`입니다. 적용 경로가 확인된 고위험·출시·이전 평가 사례에서도 목적·준수 영향이 미확인이면, 계획의 공백처럼 상위 검토 사유가 없는 경우 `CONTEXT_REQUIRED`가 됩니다. 정보 부족 자체를 적용 제외 근거로 사용하지는 않습니다.

같은 입력에 여러 조건이 해당하면 상세 이유와 규칙 추적을 함께 읽어야 합니다. `OUT_OF_SCOPE`도 모든 법적 의무의 부재를 뜻하지 않습니다. 비고위험 시스템의 목적 변경으로 고위험 시스템이 될 수 있는 경우를 포함해, 이 도구의 제한된 경로 밖에 별도 검토 사항이 있습니다.

## 3. 맥락에 따른 변경 분류체계

아래 항목은 **검토 가설**이며 위험 등급을 미리 확정하는 목록이 아닙니다.

| 변경 범주 | 가능한 영향 | 확인할 근거 |
| --- | --- | --- |
| 리팩터링·동일값 변환 | 구현은 바뀌어도 일부 고정 검사 입력은 같을 수 있음 | 실제 검사 입력의 동일성, 실행 의미·의존성, 평가 범위 |
| 정규화·스케일링·양자화 | 값의 범위, 경계 근처 예측, 공격 효과 변화 | 정상·경계·공격 입력, 정책, 수치 실행 조건 |
| 리사이즈·보간·자르기 | 유효 정보나 공격 패턴이 제거·증폭될 수 있음 | 공간 변환 조건, 관련 공격, 평가에 포함되지 않은 입력 |
| 결측값·범주 처리 | 특정 집단의 표현과 오류 분포 변화 | 집단별 결과, 누락 패턴, 대상 집단과 데이터의 대표성 |
| 보호조치 제거·수정 | 기존 평가가 전제한 방어 기능의 약화 | 보호조치의 목적, 위협모델, 회귀시험과 실패 근거 |
| 런타임·라이브러리 변경 | 계산 순서, 결정성, 지원 연산 변화 | 실행 명세, 재현성, 비교 결과, 빠진 외부 상태 |
| 입력 집단·운영 조건 변경 | 기존 근거가 새 맥락을 대표하지 못할 수 있음 | 대상 집단, 사용 조건, 새로운 위해·권리 영향 |
| 사용 목적 변경 | 같은 모델·평가 입력에도 법적 평가 맥락이 달라질 수 있음 | 목적 정의, 사용자 안내·기술문서, 적용 법령 검토 |

입력 JSON의 변경 유형은 이 분류를 기록하기 위한 간단한 태그입니다. 집단·목적 변화는 별도 필드로 기록합니다. 연산 이름에서 보호조치 변화나 법적 효과를 자동 추론하지 않습니다.

## 4. 검토 체크리스트

| 질문 | 최소한 남길 기록 | 정보가 부족할 때 |
| --- | --- | --- |
| 어떤 주장을 재사용하려는가? | 고정 평가 이름, 대상 시스템·버전, 통과 기준과 범위 | 주장을 좁혀 다시 정의 |
| 기존 통과를 확인할 수 있는가? | 보고서·실행 기록 참조, 검토자, 생성 경위 | 결과 재사용 보류 |
| 무엇이 바뀌었는가? | 전처리 코드·설정·보호조치·환경의 변경 요약 | 변경 영향 조사 |
| 실제 검사 입력과 계산 조건은 같은가? | 여섯 지문과 생성·직렬화 명세 | 누락 근거 보완 또는 관련 평가 실행 |
| 관련 의존성이 빠지지 않았는가? | 평가 주장별 의존성 목록과 검토 근거 | 숨은 의존성 조사 |
| 실패나 회귀가 알려졌는가? | 시험 상태, 실패 범위, 실행 기록 참조 | 실패 원인 조사와 새 근거 확보 |
| 고정 평가 범위가 현재 맥락을 대표하는가? | 위협모델, 입력 집단, 평가되지 않은 조건 | 평가 범위 재설계 |
| 최초 적합성 평가에서 무엇을 예정했는가? | 계획·조건·한계와 최초 평가 문서의 구체적 위치 | 규제 검토에 전달 |
| 평가된 사용 목적이나 요구사항 준수에 영향이 있는가? | 목적 정의, 영향 분석, 적용 법령·판본 | 법적 맥락 확보 및 사람의 검토 |
| 누가 어떤 근거로 결정했는가? | 작성자·검토자·결정 시점, 후속 조치와 남은 불확실성 | 책임자와 기록 보완 |

필드에 참조 문구를 입력했다는 것과 참조 대상이 검증되었다는 것은 다릅니다. 판정 엔진 v0.1은 URL이나 파일을 열어 내용을 검증하지 않으며, 검토자 이름도 신원을 인증하지 않습니다.

## 5. EU AI Act와의 개념적 대응

**사용 판본:** 2024년 6월 13일 제정, 2024년 7월 12일 관보에 게재된 Regulation (EU) 2024/1689 원문. 아래 매핑은 해당 판본의 선택한 조항에 한정합니다. 후속 개정, 적용일, 지침과 판례를 반영하는 현행 법령 판단 엔진이 아닙니다. [EUR-Lex 제정 원문](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng)

| 조항 | 연구 도구와의 대응 | 자동 결론을 내릴 수 없는 이유 |
| --- | --- | --- |
| Article 3(23) | 출시·사용 개시 이후인지, 최초 적합성 평가에서 예정되었는지, 요구사항 준수 또는 평가된 목적에 영향이 있는지 질문 | 사실관계와 법적 의미의 해석이 필요하고, 시험 결과 하나가 준수 전체를 대표하지 않음 |
| Article 43(4) 첫 문단 | 이미 적합성 평가를 받은 고위험 AI의 실질적 변경을 새 적합성 평가 검토로 연결 | 단순 소프트웨어 변경 여부만으로 substantial modification을 확정할 수 없음 |
| Article 43(4) 둘째 문단 | 계속 학습하는 고위험 AI에서 최초 평가 때 예정되고 기술문서에 포함된 변경이라는 조건을 별도 검토 | 모든 계획된 전처리 변경에 대한 포괄적 면제 조항으로 볼 수 없음 |
| Annex IV 2(f) | 예정된 변경, 성능, 지속적 준수를 확보하는 기술적 해결책을 기술문서와 연결 | 계획 참조 문자열의 존재가 문서 내용이나 평가의 적절성을 입증하지 않음 |

Article 3(23)의 실질적 변경 정의와 Article 43(4)의 계속 학습 관련 규정을 구분해야 합니다. 판정 엔진 v0.1은 계속 학습 여부나 계획 문서의 내용까지 확인하는 전용 판단 경로를 구현하지 않았습니다. 따라서 `plannedChange=yes`와 `planReference`가 있어도 법적 예외를 적용했다고 출력하지 않습니다. `DOCUMENTED_PATH`는 제출된 계획과 맥락의 기록 상태일 뿐입니다.

공식 조항 안내: [Article 3](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-3), [Article 43](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-43). 공식 안내 페이지와 현행 통합본의 판본은 다를 수 있으므로 원고 인용과 실제 적용 판단에서 별도로 확인해야 합니다.

“재인증”이라는 표현은 새 적합성 평가가 항상 외부 기관의 인증을 뜻하는 것으로 오해될 수 있습니다. 이 문서에서는 **새 적합성 평가 검토**라는 표현을 사용합니다.

## 6. 원고가 뒷받침하는 부분과 남은 검증

원고 ver3는 정상 게이트 표본의 예측 일치만으로 알려진 공격 조건의 보안 평가 통과를 재사용하면 잘못된 재사용이 발생할 수 있다는 통제된 반례를 제시합니다. 알려진 공격 관련 오류는 `mask_br` 방어 기능 제거라는 단일 기전에 집중됩니다. 많은 전환은 같은 모델·분할·경로를 공유하므로 독립적인 여러 종류의 위험 기전으로 셀 수 없습니다.

이 결과는 “모델 동일성이나 정상 예측 일치만으로 충분하지 않다”는 동기를 제공하지만, 위 분류체계의 모든 범주, 사람의 판단 개선, 평가 비용 절감, 법적 판정 정확도를 검증하지 않습니다. 원고의 의존성 키 비교 B는 포함 전환을 모두 재평가하여 재사용 능력을 입증하지 못했습니다. 실제 검사 입력 지문 기준 E의 생략은 해당 구성의 동일값 전처리 사이에서 발생했습니다.

도구에 포함된 합성 사례는 규칙을 설명하고 소프트웨어 분기를 검사하기 위한 자료입니다. 이 사례의 결과를 원고의 새 실험 결과로 합산하거나 거버넌스 프레임워크의 실증 검증이라고 표현해서는 안 됩니다. 후속 연구 설계는 [RESEARCH_PROTOCOL.md](RESEARCH_PROTOCOL.md)에 분리했습니다.
